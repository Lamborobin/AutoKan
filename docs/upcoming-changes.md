- **Per-role progress tracking** — replace the single global `progress` field on a task with per-role progress derived from each agent's own checklist. Today progress is a manually set integer (0–100) that only makes sense for the coder; PM runs, tester runs, and any other capability contribute nothing to it. The rework: each capability that has a checklist (the PM already writes `pm_checklist`; the coder and tester would write their own structured checklists) exposes its own completion ratio — resolved items ÷ total items — displayed as a small labelled progress bar per role inside the task card and detail panel. The single global bar is removed from the card exterior. A task with three roles (PM, Developer, Tester) would show three separate bars, each only visible once that role has started and produced a checklist. Implementation touches: `task_logs` or a new `task_role_checklists` structure to store per-role items; the runner prompts for coder and tester updated to emit structured checklists the same way the PM does today; the card and detail UI updated to render per-role bars instead of one global bar.

- **Per-capability context file filtering** — currently every `.md` file in `instructions/{sub}/{proj}/` is loaded for every agent regardless of capability. The PM reads the tech stack, the developer reads the client brand values — all of it goes to everyone. The fix: support an optional `audience` front-matter field on instruction files (e.g. `audience: [perm_coding, perm_coding_tester]`). The context loader respects this when building each agent's bundle — the PM only gets files with no audience restriction or `audience: [perm_planning]`. This enables clean file separation: `client.md` and `project.md` for all agents, `tech.md` for developers and testers only. Until this is built the workaround is section markers inside `project.md` and PM prompt instructions to ignore technical sections.

- **Rule-compliance benchmark (per layer)** — a way to empirically check that the layered context stack (System Rules → Workspace rules → Board rules) actually holds its waterfall invariant: a lower layer only adds constraints, never contradicts a higher one. Works by *blind testing*: the harness never tells the planner which layer is under test or adds any "this is a benchmark" awareness to its context — it just makes sure the real context stack in force for a given board/workspace is whatever it is, creates a real probing task through the exact same `POST /api/tasks` → `dispatch()` → `runClarifyAndApprove()` path a genuine task takes (no parallel/duplicate tool set for "testing mode" — the probe does exactly what real PM planning does, so it can't quietly drift from reality), and lets the planner behave normally. Cases are cumulative, not isolated: a board-level case is global System Rules + the active workspace rule (if any) + that board's own real context, all together, exactly as a genuine task on that board would see it. Every run automatically gets a deterministic check (right tool fired, checklist shape, required/forbidden content); reaching an actual reviewed status is then on demand, per run — either click "Review with AI" for a judge verdict, or manually rate the raw output on a 5-level scale (Unacceptable / Less Acceptable / Accepted / Very Good / Fully Satisfied). Each run records which review method was used and which version of the context files was in force at the time. This targets rule-compliance specifically, not general acceptance/bounceback-rate analytics on real tasks — a broader real-task-outcome dashboard (tracking `accepted`/`bounced`/`discontinued`/`revised` planning sessions) remains a separate, unbuilt future effort. v1 seeds exactly one case per layer currently visible/editable to users (System Rules, Workspace, Board — Personality is cosmetic and excluded; code/runner-prompt layers are invisible and untestable directly), to prove the pipeline before growing a case library:
  1. **Global-baseline case** — a neutral substrate (a board/workspace with zero extra workspace or board rule docs, so the only thing in force is `docs/rules.md`) — needs to actually be set up, since no such neutral board exists today.
  2. **Workspace case** — same neutral substrate, plus one workspace-level rule doc added on top, to test global+workspace combined.
  3. **One board case per existing board that already carries real board-level context** — currently 5 (`prj_a1b2c3d4` Velour/software, `prj_steel001` Steel/manufacturing, `prj_health01` Health, `prj_finance01` Finance, `prj_nordvik01` Nordvik). Each reuses that board's real, already-existing rule docs (via an AI-suggest-from-board-docs flow, or seeded/manual authoring) rather than inventing new synthetic content, since board-granularity testing is specifically about whether the planner gets *that* board's real rules right, on top of whatever global+workspace rules also apply.

  Per case, deterministic checks (tool fired, checklist shape, required/forbidden content) cover structural correctness; the on-demand AI-judge or manual review covers whether a rule was actually respected in substance — the global and workspace cases lean more deterministic since the probe is synthetic and precise, while board cases (testing against real, more open-ended rule docs) lean more on judge/manual review.
