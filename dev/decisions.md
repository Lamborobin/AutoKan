# Decisions

This file is **information only** — a running log of decisions made between the user and the AI agent, kept for future context. It does not impose rules or constraints on agents.

Update this file when a significant decision is made or reversed. Once a decision's reasoning is fully captured in a reference doc (`dev/architecture.md`, `dev/conventions.md`, `dev/agents.md`, etc.) or README, remove it from here — this log is for context not yet settled elsewhere, not a permanent history.

---

**2026-08-19 — Outward effects are gated at one boundary by run mode, rather than each handler checking whether it's a benchmark.** Benchmark probing tasks run the real handlers through the real dispatch — which meant they also produced real outward effects, so every probe that escalated to Human Action was notifying and emailing real project members. The obvious fix was an `is_benchmark_probe` check inside each handler, but that scatters the decision across every current and future handler and fails open the first time someone forgets one. Instead every outward call routes through `effects.js`, which resolves a run mode from the task and consults a policy table keyed by (run mode × effect kind); handlers and hooks declare *what kind* of effect they produce and never decide whether it fires. Suppressed effects are recorded as ordinary `note` task logs because benchmark scoring already reads that convention, which made suppression scoreable with no new wiring. Transport (branch pushes) was deliberately left ungated *and* un-renamed — it carries work between pipeline stages and is the only shared state once handlers stop sharing a filesystem, and an earlier plan to push probes to a `benchmark/` namespace was dropped once it became clear the runner prompt hands the agent its own branch and push command, so a benchmark-only name would simply make the prompt wrong and the push fail. That sharpened the rule: effects the agent triggers but never acts on can be suppressed invisibly, while anything it operates on must stay true. Probe branches are identified for cleanup from the run record instead. Rejected wiring the gate to `acceptance_criteria` prose: that would let text an agent reads decide whether a real email goes out, contradicting the rule that no prompt layer can change what the code permits. Per-run enablement instead lives in a structured `allowed_effects` list on the benchmark case, matched by effect id so opting one effect in never unlocks another — distinct from the still-unbuilt per-capability allow-list, which asks whether a capability may invoke an action at all rather than whether this run really performs it.

**2026-08-14 — `verify_document` discovers the board's document standard by listing, not by filename.** The demo boards don't agree on a name for the producer's guide file (`doc-guide.md` for healthcare/finance/Nordvik, `sop-guide.md` for manufacturing), and that file's front matter scopes it to `perm_producing` — so it's deliberately excluded from a `perm_verifying` agent's auto-loaded context, the same filter that already keeps producer/tester personas from leaking into the wrong agent. Rather than hardcode a filename (which would silently break on manufacturing) or special-case the capability filter, `verify_document`'s runner prompt tells the agent the board's instructions folder path and has it list + read whatever's there via its own tools. Keeps the handler sector-agnostic with no seed renames.

**2026-08-14 — Board/workspace markdown can override `produce_document`'s output path convention, within the write-scope the code already enforces.** `produce_document`'s runner prompt has the agent check its context for an explicit output folder/naming convention (e.g. "put reports under a folder named for the year") and follow it if present, falling back to a simple default otherwise. This is safe because `writeFileSafe`/`validateWritePath` still hard-enforce that every write stays inside the board's own write scope regardless of what the markdown says — the markdown can only choose *where within* the enforced scope, never escape it. Matches the existing model where instruction files are personality/convention, not a second source of mechanical enforcement. (Superseded in scope by the next entry — the enforced folder is now the board's linked `client_path`, not a flat shared folder.)

**2026-08-14 — Benchmarking `perm_verifying` runs `perm_producing` first, against a real document, rather than a planted fixture.** The benchmark system previously only supported `perm_planning`, which resolves in one dispatch. Verify can't meaningfully run from a bare title+description — it needs a real document to check first. `createRunAndDispatch` (in `benchmarkRunner.js`) now dispatches a Producing probing task on the same brief, waits for it to settle, and only then dispatches the Verify probing task (same title, so Verify's own filename-agnostic discovery finds it) — `benchmark_runs.source_task_id` records the upstream Producing task for traceability, while `probing_task_id` stays the task actually scored. Chose this over a manually-planted fixture so Verify benchmark cases stay self-contained and blind, consistent with how Planning cases already work. Deterministic/judge scoring machinery (`OUTCOME_TOOL_SIGNALS` → `CAPABILITY_PROBES`, `scoreDeterministic`, `callJudge`) was generalized into a per-capability lookup table rather than left Planning-only or branched inline. Requires a `capability` column on `benchmark_cases` (defaults to `perm_planning` for existing rows) — needs `npm run db:reset` to take effect, not yet run.

**2026-08-14 — `produce_document`/`verify_document` write into the board's own linked folder (`projects.client_path`), not a flat shared `client/docs/`.** The original implementation used a single hardcoded `client/docs/` for every board — which meant an unlinked board (no folder/repo connected via Board settings → Connections) would still silently accept writes into a location unrelated to any specific client, and a benchmark run against such a board would hang waiting for a task whose dispatch never made sense. Fixed by: (1) a new `{clientPath}` template var in `writeGuard.js`'s `resolveTemplateVars`, resolved from `projects.client_path` and falling back to a path that can never exist (fail closed) rather than a plausible-looking default; (2) `perm_producing`'s `write_access` changed from `"client/docs/"` to `"{clientPath}/docs/"`; (3) a new `requireLinkedClientPath()` guard at the top of both handlers that checks the board actually has a `client_path` pointing at a folder that exists on disk *before* any LLM call or write attempt, escalating straight to Human Action with a clear reason if not. Mirrors how `perm_coding`'s worktree already operates inside a specific project — Producing/Verifying just weren't scoped to it before.
