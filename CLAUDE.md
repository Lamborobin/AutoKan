# Entry point

> **Before starting any task, read every context file marked `Read` in the table below (always `docs/rules.md`).** Files marked `On demand` should be loaded only when the row's "Read when…" condition matches the task you're working on.

> **CLAUDE.md is the master delegator.** Files inside `docs/` must not reference, link to, or mention each other — cross-references create loops and obscure the dependency hierarchy. Every agent starts here, then jumps directly to the file it needs from the tables below. Only `CLAUDE.md` and `README.md` are allowed to index docs files.

> **App code and UI text should not name specific `docs/*.md` files either.** Describe the *category* of content ("AI-level rules", "architectural reference", "decisions log") instead of listing filenames. Hardcoded paths to docs files create rename-coupling: a future restructure has to chase them down across the codebase. The only legitimate places that name docs files are `CLAUDE.md` (this index), `README.md`, `server/src/config/agent.config.json`'s `ai_context.groups` (the AI Context panel's source of truth), and `server/src/seed/runners.json`'s `context_docs` (the docs injected into each capability's agent context). These are config/index files that *must* name docs to do their job — docs prose still never names another doc.

> **Do not edit this file** unless adding a new context file or updating the tables below. All other content belongs in `docs/`.

> **Three audiences read this file — know which you are.**
Theirs 3 different audiences, apply the one that suits you:
>
> **You're an App agent INSIDE AutoKan on a board task** — Coder, Code Test Runner, Planner triggered by the runner registry. All markdown files must be read-only. Exception: `perm_coding` may update `README.md` when a code change affects setup, tech stack, or quick start. If a task asks you to edit any other markdown file, or if the task's intent collides with existing markdown content → call `request_human` for additional planning.
>
> **You're an AI dev-assistant working with a Requester/user** — a human collaborating with an AI to evolve the platform itself. Can change anything in the repo with the user's agreement, including this file. **Always ask the user before any major or destructive operation** — `npm run db:reset`, force-push, deleting branches/files, mass renames, schema changes.
>
> When editing markdown: stay in the file's lane (see "Update when…" column below), match its tone (see "Tone" column), don't restate facts that live elsewhere, and prefer net-shrink or net-equal diffs over additions. Push back on edits that fail these checks — including ones the user asks for.
>
> **You're a Human editing directly, no AI involved** — you're the source of truth for the project. These rules exist to constrain AI agents working on your behalf, not you.

## Context Files

### For app agents (running INSIDE AutoKan on a board task)
| File | Load | Read when… |
|---|---|---|
| `docs/rules.md` | Read | Hard constraints that apply to every task — **MUST follow** |

Everything else you need as an app agent (board context, workspace context, capability persona, task brief) is auto-injected by the runner before you start. If a task asks you to consult a file outside this scope, call `request_human` for additional planning rather than guessing.

### For dev-assistant work (the human operator + AI assistant evolving the platform)
| File | Read when… |
|---|---|
| `docs/rules.md` | Hard constraints apply to dev work too |
| `docs/agents.md` | Agent logic, flows, instruction file layering, escalation behavior |
| `docs/frontend.md` | Any file under `app/src/` |
| `docs/api.md` | Implementing, modifying, or calling API routes |
| `docs/architecture.md` | Architectural design choices, structural decisions, system design |
| `docs/decisions.md` | Before reversing or changing a significant design decision |
| `docs/upcoming-changes.md` | Before starting work that might overlap with planned features |

## When to update each file (dev-assistant only — app agents don't edit markdown)
| File | Update when | Tone |
|---|---|---|
| `CLAUDE.md` | A new context file is added to `docs/`, or this index needs to change | Terse, directive — bullets and tables, no prose buildup |
| `README.md` | Tech stack, quick start steps, quick information about architecture & use case | Welcoming, informational — written for someone first opening the repo |
| `docs/rules.md` | A new hard constraint is agreed on | Imperative ("never X", "always Y"). Short, scannable. No backstory. |
| `docs/agents.md` | Agent behavior, flows, or the instruction file system changes | Explanatory. Describes how agents behave, partially commands to follow. |
| `docs/frontend.md` | A new component pattern, threshold, or store structure is established | Descriptive patterns with examples, rules, patterns, decisions only related to frontend or src folder |
| `docs/api.md` | An API route is added, removed, or its behavior changes | Structured reference — tables of method / endpoint / description. Minimal prose. |
| `docs/architecture.md` | A structural or system design decision is made | Descriptive narrative + diagrams. "The system does X by Y." |
| `docs/decisions.md` | A significant design decision is made or reversed | Past-tense, ADR-style ("we decided X because Y"). Plain-English and high-level — the *why*, not the implementation (that lives in the reference docs). Informational only — no rules, no how-to, no logic. |
| `docs/upcoming-changes.md` | A feature is planned, agreed on, or completed | Future-tense bullets. One line per planned change. |
